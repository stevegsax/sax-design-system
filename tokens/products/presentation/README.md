# presentation

Token overrides for the `presentation` product — reveal.js slide decks. One override: the dark-mode page is true black (`{color.neutral.0}`) for projectors and OLED displays.

The build emits the deck kit to `dist/presentation/`: `reveal.js`, `reset.css`, `reveal.css`, `tokens.css`, `theme.css`, the optional `highlight.js` + `highlight.css` (syntax highlighting), and a sample `presentation.html`. This file records what we learned wiring the tokens to reveal.js, so the lessons survive the next theme change.

## reveal.js styling is two layers, and reveal ships only one of them

1. **`reveal.css` — structure.** Slide positioning, transitions, fragments, controls, the progress bar. It deliberately contains almost no typography or color. The one thing it hardcodes is `.reveal-viewport { background-color: #fff }` as a fallback, and the only `--r-*` variables it reads itself are the controls/scrollbar/overlay ones.
2. **A theme stylesheet.** In stock reveal.js this is `theme/white.css`, `black.css`, etc. The theme is what consumes the `--r-*` custom properties (`--r-background-color`, `--r-main-color`, `--r-heading-margin`, `--r-block-margin`, …) and applies them to actual elements.

Setting a CSS variable does nothing on its own — something has to read it with `var()`. Our kit ships no stock theme, so `dist/presentation/theme.css` (generated by `scripts/build-presentation.js`) is that layer: it maps the token custom properties onto `--r-*` and then consumes them. Decks link, in order: `reset.css`, `reveal.css`, `tokens.css`, `theme.css`.

reveal.js documents its theme-authoring model — the settings/template split and the full `--r-*` variable list — at <https://github.com/hakimel/reveal.js/blob/master/css/theme/README.md> (source in [`css/theme/template/settings.scss`](https://github.com/hakimel/reveal.js/blob/master/css/theme/template/settings.scss) and [`theme.scss`](https://github.com/hakimel/reveal.js/blob/master/css/theme/template/theme.scss)). Our `theme.css` follows that model — the `:root` block is the themeable surface, the rules below apply it — with the deliberate deviations noted in [How our theme maps to reveal's variables](#how-our-theme-maps-to-reveals-variables).

We learned this the hard way: an earlier version declared every `--r-*` variable and consumed none of the structural ones. Each bug below is the same failure class — declared but never (correctly) consumed.

## Failure modes a deck hits without the theme layer

- **White-on-white in dark mode.** `tokens.css` declares `color-scheme: light dark`, so heading/text tokens resolve to near-white on a dark-mode OS — while the background stayed reveal's hardcoded `#fff`. The theme layer must set `.reveal-viewport { background-color: var(--r-background-color) }` and `.reveal { color: var(--r-main-color) }`.
- **All typographic spacing collapses.** reveal's `reset.css` zeroes every margin and padding; the theme layer is what restores heading and block margins (`--r-heading-margin`, `--r-block-margin`).
- **List bullets clip off the slide edge.** Zeroed `padding-inline-start` puts markers outside the content box. Restore it (`1.2em`).
- **Bold and italic silently disappear.** The reset applies `font: inherit` and `vertical-align: baseline` to `strong`, `em`, `b`, `i`, `sup`, `sub`. Stock themes restore these; ours must too.
- **Centered-slide fights.** reveal centers slide content (`text-align: center`). Left unmanaged, list text centers per-line away from its bullet and every code line centers individually. Stock-theme fix, adopted in ours: lists are `display: inline-block; text-align: left` (the block centers, its content doesn't), and `pre` gets `text-align: left`.
- **Code blocks pad only their first line.** reveal.css leaves `pre code` as an *inline* element — `display: block` is the stock theme's job, not structure's. On an inline box, `padding` applies only at the box's start and end, so reveal's `pre code` padding lands before the first line and after the last, and every line in between sits flush against the left edge. The fix is `display: block` on `.reveal pre code` (then padding becomes a normal box and every line is inset); ours also bumps the padding to `--space-xl`. Watch the specificity: reveal ships `html:not(.print-pdf) .reveal pre code { padding: 20px }`, which outranks a plain `.reveal pre code` — a bare `.reveal pre code { padding: … }` is silently ignored no matter that `theme.css` loads later. Match reveal's selector (`html:not(.print-pdf) .reveal pre code`) so source order decides and ours wins.

## Contracts that fight the token architecture

- **The overlay/scrollbar variables are RGB triplets, not colors.** reveal.css consumes `--r-overlay-element-{bg,fg}-color` as `rgba(var(--…), .4)` — it expects a bare `R, G, B` triplet (stock themes declare e.g. `240, 240, 240`). A `light-dark(oklch(…))` value makes every consuming declaration invalid at computed-value time, which renders as transparent. There is no way to express a mode-conditional triplet, so `theme.css` instead overrides the consuming rules (the scroll-view scrollbar) directly with `color-mix(in srgb, var(--color-text-body) N%, transparent)`. If the pinned reveal.js version is bumped, re-check those selectors against the new `reveal.css`.
- **`font` shorthand owns weight.** Typography tokens are `font` shorthand values, so heading weight comes from `--typography-heading-*`; a `--r-heading-font-weight` declaration can never win and was removed. Don't declare knobs the cascade makes unreachable.
- **True black squeezes the background ramp.** With `background.page` overridden to `{color.neutral.0}`, the dark inset (`{color.neutral.5}`) renders `#000001` — indistinguishable from the page, so code blocks are delineated by their border alone. If a visible inset matters, this product would need to remap `background.inset` upward (a token value change with APCA implications), not a theme.css change.

## How our theme maps to reveal's variables

`theme.css` follows reveal's settings/template structure: the `:root` block is the themeable surface (grouped as in reveal's `settings.scss` — background, main, headings, links, selection), and the rules below apply it. Three deliberate deviations from the stock template:

- **Typography is a composite, not discrete font variables.** reveal's template exposes `--r-main-font`, `--r-heading-font`, `--r-heading-font-weight`, `--r-heading-line-height`. Our typography tier ships `font` *shorthand* composites (`--typography-heading-1`, etc.) that bundle family, weight, line-height, and a base size, and the primitives behind them are not emitted as standalone custom properties. So `.reveal` and the headings set `font: var(--typography-*)`, and those four discrete `--r-*` variables are intentionally absent. Do not re-add `--r-heading-font-weight`: the composite owns weight, so the variable can never win the cascade (it was removed for exactly this reason).
- **Heading sizes are the one typographic knob kept as `--r-*` variables.** `--r-heading1-size`/`2`/`3` are slide-display multipliers of `--r-main-font-size` (reveal scales headings relative to a fixed slide base, not the token's absolute size). They override the composite's size after the `font` shorthand — which is why the size declaration must come after, and why only colour/margin/letter-spacing/etc. (properties the `font` shorthand does not reset) live in the shared `h1`–`h6` rule.
- **`light-dark()` replaces reveal's dark-link variable.** reveal offers `--r-link-color-dark` for dark backgrounds; every token here is already a `light-dark()` pair, so one `--r-link-color` covers both modes and the dark variant is unused.

What we apply that the reset would otherwise eat (covered in the failure-modes section above): heading/block margins, list indentation, `strong`/`em`/`sup`/`sub`, left-aligned lists and code, and the scroll-view scrollbar. Beyond that, the theme also styles `h1`–`h6` (not just the `h1`–`h3` the deck uses) and tables (`th`/`td` with token borders), matching the template's selector coverage so a consumer deck using those elements is themed without extra CSS.

## Syntax highlighting

Code highlighting uses reveal's highlight plugin (which bundles highlight.js). The kit ships the plugin (`highlight.js`) and a **token-driven** color theme (`highlight.css`) instead of a stock hljs theme — monokai/zenburn are fixed dark palettes that ignore the tokens and fight the page background. `highlight.css` maps the hljs token classes onto semantic colors:

| Syntax role (hljs classes) | Token |
| --- | --- |
| keyword, built\_in, type, section, deletion | `color.status.danger.text` |
| string, regexp, attr, addition, selector-attr | `color.status.success.text` |
| number, literal, symbol, bullet | `color.status.warning.text` |
| title, name, attribute, selector-id, template-tag | `color.text.link` |
| comment, quote, meta | `color.text.muted` |
| variable, template-variable, subst, default text | `color.text.body` |

Because the colors are tokens, code follows `light-dark()` automatically and is held to the **same APCA gates** as the rest of the system: each role is a pair against `color.background.inset` (the code background) in `config/contrast-pairs.json` — default code text at Lc 75, the colored roles at 60 (the grade links use; on the true-black dark page, brand-at-0.80 reaches ~67, so 75 is unreachable for colored syntax there without flattening the palette to near-white).

Wiring (in `scripts/build-presentation.js`, reflected in the sample deck):

- Link `highlight.css` after `theme.css`; load `highlight.js` after `reveal.js`.
- Register the plugin: `Reveal.initialize({ plugins: [ RevealHighlight ] })` (the script exposes the `RevealHighlight` global).
- Mark code blocks with a language: `<pre><code data-trim class="language-javascript">`. **Give every code block an explicit language** (`language-plaintext` for non-code listings) — with `highlightOnLoad` the plugin auto-detects unlabelled blocks, which mis-colors ASCII/tabular listings.

`highlight.css` and `highlight.js` are optional: a deck with no code need not link them.

## Verifying a theme change

Reading the CSS is not enough — these bugs were all found by rendering. Headless Chrome, no toolchain needed:

```sh
CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
"$CHROME" --headless=new --disable-gpu --hide-scrollbars --window-size=1280,800 \
  --virtual-time-budget=6000 --screenshot=slide.png \
  "file:///path/to/presentation.html#/1/0/2"
```

- The hash picks the slide; `#/1/0/2` also reveals fragments (slide 1, all three fragments shown).
- Force dark mode by inserting `<style>:root{color-scheme:dark}</style>` before `</head>` in a copy — `light-dark()` follows the element's used `color-scheme`, so this flips every pair without touching the OS. (A `prefers-color-scheme` media query would not respond to this technique; that is one reason the system uses `light-dark()`.)
- Check the scroll view too (`presentation.html?view=scroll`) — it exercises the scrollbar overrides.
- Verify both modes, and verify `<strong>`/`<em>`, list geometry, code-block alignment, and syntax highlighting, not just colors: those failures are silent. The highlight plugin runs JS, so give the headless render a virtual-time budget (e.g. `--virtual-time-budget=8000`) or the code renders unhighlighted.
